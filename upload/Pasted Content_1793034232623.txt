# GOD-TIER PROJECT PROMPT — DeutschFlow
## Premium German Learning Platform | Listening • Pronunciation • Vocabulary • Speaking

You are a principal software engineer, senior product designer, German phonetics specialist, performance engineer, and QA architect.

Build **DeutschFlow**, an exceptionally polished, fast, mobile-first German learning web application designed primarily for Bengali-speaking learners progressing from A1 to B1 and beyond.

This must be a real, production-quality application—not a prototype, static mockup, or collection of disconnected components.

The product should combine the best ideas from modern language-learning apps, premium audio tools, vocabulary trainers, and minimalist productivity software into one coherent experience.

The core experience is:

**Type anything → automatically detect the language → obtain the correct German text → hear natural German pronunciation → see reliable Bengali pronunciation → understand the meaning → save useful vocabulary → review it later.**

Every interaction must feel intentional, immediate, and beautifully animated.

# 1. NON-NEGOTIABLE PRODUCT PRINCIPLES

1. Language detection must happen automatically.
2. German input must play directly without translation.
3. English and Bengali input must be translated into German when appropriate.
4. German audio must use a genuine German speech engine, not English TTS pretending to pronounce German.
5. Bengali pronunciation must be generated from German pronunciation rules or a suitable phonetic engine—not by blindly replacing letters.
6. The user must be able to save individual words, complete sentences, meanings, and pronunciation notes to a personal vocabulary collection.
7. Frequently used translations, pronunciation results, and audio must be cached intelligently.
8. Repeated actions should be extremely fast.
9. The entire application must work beautifully on phones, tablets, laptops, and desktop monitors.
10. Never fake functionality, fabricate API responses, or claim that an unsupported feature works.
11. Prefer free, local, open-source, and low-cost solutions when they provide sufficient quality.
12. No unnecessary authentication, infrastructure, dependencies, or paid services.

Before writing code, inspect the existing repository, installed packages, project architecture, deployment environment, and available configuration. Preserve useful existing work. Do not blindly replace the project or introduce a new framework without justification.

This is the heart of the application. Spend the greatest amount of design and engineering effort here.

## Input area

Provide one excellent multilingual text input.

Placeholder:

Requirements:

The primary button should be visually prominent and say:

**Listen Now**

On desktop, provide an appropriate keyboard shortcut and display it unobtrusively.

## One-action processing pipeline

When the user submits text, execute this pipeline:

1. Normalize whitespace without changing meaningful spelling or punctuation.
2. Detect the probable input language.
3. Determine whether the text is German, English, Bengali, or ambiguous.
4. Apply the appropriate processing route.
5. Obtain German text if translation is necessary.
6. Generate or retrieve the Bengali pronunciation.
7. Prepare the German speech engine.
8. Start playback as soon as the required German text and speech engine are ready.
9. Display the German sentence, Bengali pronunciation, and meaning.
10. Save the result in local history when appropriate.

For short inputs, optimize for minimal perceived latency.

**Do not wait for optional explanations, word analysis, or vocabulary metadata before starting audio.** Load these details progressively after the main result is available.

For German input, do not call the translation provider unnecessarily.

For English and Bengali input, do not play the original English or Bengali text as the German result.

When a translation or pronunciation provider fails, display an understandable error and provide an appropriate retry action.

## Processing states

Implement explicit states:
- Idle.
- Detecting language.
- Translating.
- Preparing audio.
- Playing.
- Paused.
- Finished.
- Failed.
- Cached result ready.

Avoid flashing several unnecessary loading indicators during a fast cached response.

If German audio is already available, start playback immediately after the user's gesture whenever browser policies permit.

If the text requires translation, begin playback immediately when the translated German text becomes available. Do not falsely claim that translation or playback has completed before it actually has.

# 6. GERMAN PRONUNCIATION ENGINE — CRITICAL

Build this as an independent, replaceable module.

The pronunciation engine must understand that German spelling, phonetic pronunciation, audio synthesis, and Bengali transliteration are related but distinct.

## The `ihr` problem

The app must handle words such as:

`ihr`

Expected result:

German text:
`ihr`

Bengali pronunciation aid:
`ইয়া` or another carefully selected Bengali approximation appropriate to the configured pronunciation standard.

Do not blindly produce `ঈয়ার` by copying an assumed final `r` into Bengali. In standard German, the `r` in this word is commonly vocalized rather than pronounced as a strong Bengali-style consonant. The exact realization varies by accent and speaking context.

The actual German audio must remain the authoritative pronunciation reference.

## Pronunciation architecture

Implement a layered pipeline:

1. German text normalization.
2. Word tokenization that preserves punctuation.
3. Lookup in a curated pronunciation lexicon.
4. Lookup in a reliable German pronunciation dictionary or phonetic resource, if available.
5. IPA or equivalent phonetic representation where supported.
6. German-specific grapheme-to-phoneme rules.
7. Context-sensitive pronunciation handling.
8. Bengali-script approximation.
9. Confidence and source metadata.
10. Fallback when the pronunciation is uncertain.

Prioritize curated, verified entries for common A1/A2 vocabulary and irregular words.

Do not use a simplistic regex substitution engine as the sole pronunciation solution.

Do not invent a perfect IPA transcription when no reliable pronunciation source exists.

## German pronunciation cases

Handle, at minimum:
- `ch` in different phonetic contexts.
- `sch`.
- `sp` and `st` at the beginning of words and syllables.
- `z`.
- `w`.
- `v`.
- `j`.
- `ei`.
- `ie`.
- `eu` and `äu`.
- `ä`, `ö`, and `ü`.
- `ß`.
- Consonant clusters.
- Final consonant devoicing.
- Common unstressed endings.
- Vocalized `r`.
- Long and short vowels.
- Word stress when supported.
- Compound nouns.
- Punctuation and sentence intonation.

Avoid applying a rule blindly where lexical exceptions exist.

## Bengali pronunciation display

Present pronunciation as an accessible learning aid, not a claim of exact phonetic equivalence.

Example result card:

GERMAN PRONUNCIATION

`ihr`

**বাংলা উচ্চারণ**

`ইয়া`

"আনুমানিক উচ্চারণ — সঠিক ধ্বনির জন্য অডিও শুনুন।"

The result must be generated by the actual pronunciation pipeline, not hardcoded into the UI.

For uncertain words, show a small confidence/source indicator or offer a more detailed phonetic view.

Allow the user to report an incorrect pronunciation approximation. Save corrections locally and use them as personal overrides, rather than silently treating every user correction as a universal linguistic truth.

## Word-by-word pronunciation

For longer sentences, provide a word breakdown that preserves original German spelling and punctuation.

Example:

`Guten Morgen! Wie geht es dir?`

- `Guten` — Bengali pronunciation aid.
- `Morgen` — Bengali pronunciation aid.
- `Wie` — Bengali pronunciation aid.
- `geht` — Bengali pronunciation aid.
- `es` — Bengali pronunciation aid.
- `dir` — Bengali pronunciation aid.

Clicking a word should:
- Highlight the selected word.
- Show its meaning when available.
- Display its pronunciation.
- Allow the word to be spoken separately.
- Provide a one-click option to save it to vocabulary.

Do not require word-by-word analysis before the full sentence can play.

# 11. HIGH-PERFORMANCE CACHING ARCHITECTURE

Performance is a core product requirement.

The app must feel fast even when a translation provider is slow or unavailable.

Design caching at several independent layers.

## Layer 1: In-memory cache

Cache frequently accessed results during the current session.

Suitable entries:
- Language detection.
- Normalized German text.
- Translation results.
- Pronunciation results.
- Tokenization.
- Word metadata.

Use bounded caches with an appropriate eviction strategy such as LRU.

Avoid retaining unlimited sentence histories in memory.

## Layer 2: Persistent browser cache

Use IndexedDB for structured, reusable data.

Cache:
- Translation results.
- Bengali pronunciation results.
- Vocabulary metadata.
- Frequently used language resources.
- Reusable phonetic lookup results.
- User preferences where appropriate.

Use localStorage only for small settings and lightweight preferences.

Avoid storing large collections in localStorage.

## Layer 3: Audio cache

For external TTS providers that return actual audio:
- Cache reusable audio assets using appropriate browser storage.
- Store metadata separately.
- Reuse identical audio where the text, voice, speed, and provider configuration match.
- Handle quota limits and eviction.
- Provide cache clearing.
- Never assume that Web Speech API utterances can be saved as audio files.

For browser-native TTS, cache voice selection and prepared speech metadata, not imaginary audio blobs.

## Layer 4: HTTP and service-worker cache

If a backend and PWA are implemented:
- Use appropriate HTTP caching headers.
- Cache static assets aggressively when safe.
- Use versioned asset names.
- Avoid caching private responses as public assets.
- Use service-worker strategies appropriate to each resource type.
- Never cache API responses containing secrets.
- Provide predictable cache invalidation after deployments.

## Cache correctness

Cache keys must include all relevant parameters.

Examples:
- Normalized source text.
- Source language.
- Target language.
- Translation provider and model/version.
- Pronunciation provider and ruleset version.
- Voice identifier.
- Speech rate where applicable.
- Output format for generated audio.

Normalize only what is safe to normalize. Do not merge strings with meaningfully different punctuation, language context, or pronunciation.

Version cached results so pronunciation-rule updates invalidate outdated data.

Use TTLs where provider data can change and deterministic cache reuse where appropriate.

## Fast interaction strategy

- Start German audio without waiting for optional grammar analysis.
- Run independent metadata requests in parallel when safe.
- Debounce search inputs.
- Prefetch likely next vocabulary items only when it provides a measurable benefit.
- Avoid duplicate network requests for identical in-flight operations.
- Reuse previously fetched results.
- Cancel obsolete requests.
- Keep the main thread free during heavy processing.
- Avoid unnecessary rerenders.
- Lazy-load secondary pages and heavy libraries.
- Do not install a large state-management library unless the project genuinely needs it.

## Offline behavior

Support offline access to:
- The application shell, where PWA support is implemented.
- Previously saved vocabulary.
- Local history.
- Cached translations and pronunciation results.
- Basic phonetic rules and curated word entries.

Clearly distinguish cached/offline capabilities from online-only translation and TTS capabilities.

Never claim arbitrary new text can be translated offline unless a suitable local translation engine is actually installed.
